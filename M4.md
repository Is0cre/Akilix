# Akilix M4 — Forensic Acquisition

The first M4 slices establish typed passive hardware inventory and an explicit,
provenance-backed software read-only operation before imaging is introduced.

Implemented:

- udev kernel read-only policy for attached USB/removable whole-disk storage
- atomic `/run/akilix/device-events/` add/remove decision queue

- `akilix acquire inspect [--json]`
- `akilix acquire record WORKBOOK [--json]`
- `akilix acquire protect WORKBOOK DEVICE [--json]`
- `akilix acquire identify WORKBOOK DEVICE [--json]`
- `akilix acquire image WORKBOOK DEVICE OUTPUT [--json]`
- `akilix acquire verify WORKBOOK OPERATION_ID [--json]`
- `akilix acquire status WORKBOOK [OPERATION_ID] [--json]`
- `akilix device trust add DEVICE [LABEL]`
- `akilix device trust list [--json]`
- `akilix device trust remove TRUST_ID`
- structured `lsblk` JSON ingestion with no shell command construction
- disk, partition, filesystem, UUID, serial, WWN, transport, capacity,
  read-only, removable, and mount-state reporting
- conservative system-disk detection through root/boot mount ancestry
- explicit acquisition-candidate classification for non-system disks
- deterministic `akilix.hardware-inspection.v1` output

The inspect command does not open raw device nodes, mount or unmount filesystems, alter
kernel read-only state, invoke SMART/NVMe commands, or write to a workbook.
`acquisition_candidate` means only "not identified as the running system disk";
it is not authorization and is not proof that a device is external.

`record` is the separate explicit persistence action. It performs the same
passive inspection and atomically creates a mode-`0600` UUIDv7 record beneath
`hardware/inspections/` in an open workbook. Records contain workbook identity,
inspection and record timestamps, completion state, and the full inventory.
Existing records are never overwritten; failed writes do not leave a
valid-looking record.

`protect` accepts only an exact whole-disk path from the immediately preceding
inspection. It refuses the running system disk, mounted disks, partitions, and
unknown paths. It writes an immutable `REQUESTED` event before executing
`blockdev --setro DEVICE`, verifies with `blockdev --getro DEVICE`, and writes
an `APPLIED` or `FAILED` event under `hardware/protections/`. A request left
without a terminal event is deliberately visible as incomplete provenance.
Akilix does not invoke sudo, unmount devices, or expose an automatic write-enable
operation; privilege elevation remains an explicit operator action.

The kernel read-only bit is defense in depth only. It is not equivalent to a
hardware forensic write blocker and must never be represented as one.

The host-local device trust registry records stable block-device identities by
WWN or by the combination of serial, vendor, and model. It refuses transient
device paths and weak model-only identities. Inspection labels matching disks
as trusted, while candidate classification and read-only behavior remain
unchanged. Revocations are retained in the registry for auditability.
The acquisition layer only handles block devices; keyboards, mice, audio,
Bluetooth, and other non-storage peripherals are outside this policy and are
not passed to `blockdev`.

The ISO udev policy matches only whole-disk block events identified as USB or
kernel-removable. On attachment it requests the kernel `ro` attribute before
queuing an event, marks the device ignored for desktop automount handling, and
records whether read-only state was observable. It never matches the generic
USB subsystem, so keyboards and other non-storage peripherals are unaffected.
Events remain `PENDING` until the operator-facing decision workflow handles
them. Trust remains descriptive and never clears the kernel read-only flag.

The image contains a checksum-pinned snapshot of the public `usb.ids` database
for offline VID/PID display. No attachment event performs an Internet lookup.
Vendor and product names from this database are descriptive only and never
satisfy the stable identity requirement for trust.

When adding an attached block device to the trust registry, Akilix queries its
local udev properties with a fixed argument vector. USB devices are enriched
with numeric VID/PID values and offline friendly names. A WWN remains the
strongest available key; otherwise USB trust uses serial plus numeric VID/PID.
The older serial/vendor/model form remains matchable for registry compatibility.

`identify` refuses system, mounted, partition, and unknown device paths. Before
running a diagnostic it writes a complete passive inventory record to the
workbook. SATA/SCSI/USB storage is queried with `smartctl --json=c --all`;
NVMe storage uses `nvme id-ctrl --output-format=json` and `nvme smart-log
--output-format=json`. Exact argument vectors, exit codes, status classification,
and raw JSON are recorded under `hardware/identifications/`. SMART health exit
bits are distinguished from missing tools, tool errors, and malformed output.
The command never mounts a filesystem or writes to the target device.

`image` accepts only a whole-disk candidate from a fresh passive inspection and
refuses mounted, system, unknown, or non-read-only sources. The operator supplies
a basename created beneath `evidence/acquired/`; paths and pre-existing outputs
are refused. Akilix records `REQUESTED` before opening the destination, streams
the source without mounting it, computes SHA-256 inline, fsyncs and atomically
publishes the completed image, then records `COMPLETED`. Errors and handled
interruptions produce a distinct `FAILED` record and never publish a partial
image. Abrupt power loss still leaves the durable request record and an
unpublished temporary file for explicit recovery inspection.

`verify` independently streams the published image again and compares both its
byte count and SHA-256 digest with the immutable completion record. Every check
creates a new immutable verification record and journal event; a mismatch exits
non-zero without changing the acquired image. A request lacking a completion
record is reported as incomplete rather than treated as evidence.

`status` reconstructs acquisition state from immutable records without opening
source devices or altering partial files. REQUESTED-only and FAILED operations
are marked `recovery_required`; only a durable completion record yields
COMPLETED. Recovery is deliberately inspection-only at this stage—Akilix does
not automatically delete, resume, or bless temporary data.
