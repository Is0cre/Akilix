# Akilix M3 — Curated Profiles

The first M3 slice is metadata-only and intentionally performs no host
mutation. Profiles are versioned YAML manifests describing curated capability
sets. Installation, Snapper transaction handling, verification, and rollback
remain separate operations.

Implemented:

- `akilix.profile.v1` manifest validation
- `akilix profile list [--json]`
- `akilix profile show ID [--json]`
- `akilix profile plan ID [--json]`
- `akilix profile preflight ID [--json]`
- `akilix profile verify ID [--json]`
- `akilix profile history [ID] [--json]`
- CORE foundation profile
- planned NETWORK, WIRELESS, RECON, WEB, REVERSE, FORENSICS,
  INCIDENT-RESPONSE, and OPERATOR capability profiles
- RPM installation under `/usr/share/akilix/profiles`
- Versioned repository identity and signing-key metadata
- Offline `akilix repository list|show` inspection

Profile metadata is not an authorization boundary and does not itself install
packages or start services.

The planned catalog deliberately distinguishes conservative host utilities
from fast-moving OCI tool families. The family component contents are:

- `akilix-recon`: Naabu and ASN mapping
- `akilix-network`: additional structured network analysis tools
- `akilix-wireless-analysis`: offline analysis of operator-requested captures;
  host adapter control remains outside the container
- `akilix-web`: httpx, Katana, and Feroxbuster
- `akilix-reverse`: reproducible binary-analysis tooling
- `akilix-forensics`: read-only analysis tooling; physical acquisition remains
  a separate host subsystem
- `akilix-incident-response`: disposable host-artifact analysis tooling

These names identify future Akilix-built OCI components, not mutable remote
image tags. Before a component can become installable, it needs a reproducible
build definition, package inventory, immutable digest, and verification policy.

`profile verify` performs only local, read-only RPM database and Podman image
inspection. OCI names are resolved in the `localhost/` namespace and no pull,
repository refresh, package installation, or service action occurs. Each check
creates an immutable mode-0600 platform record beneath the configured Akilix
state directory, deliberately separate from workbook evidence and rollback
semantics. Missing components produce a complete record and a non-zero exit.
`profile history` reads those immutable records locally, in chronological order,
with an optional profile filter; it performs no new verification or host action.

`profile preflight` is also local and read-only. It checks that the root
filesystem is Btrfs, a Snapper configuration covers `/`, required native host
tools are available, and the manifest has reached foundation maturity. It
reports whether a future apply would require elevation, but never snapshots,
refreshes repositories, installs packages, pulls images, or changes services.
Apply remains deliberately unsupported until its transactional failure and
rollback behavior is implemented and tested.

`profile plan` is descriptive only. Any future apply command must preserve the
SNAPSHOT → APPLY → VERIFY transaction and retain rollback state on failure.
